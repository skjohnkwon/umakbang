# v0.2 - remote projects

Working notes for the next version. Not a spec and not a promise: the decisions here are
the ones already argued through, the open questions are the ones still worth arguing, and
the measurements are the reason most of the arguing stopped.

Status: brainstorm, nothing built. Current release is 0.1.2.

## The problem

Two machines - a PC that does the producing and a MacBook that travels. The library lives
on an NTFS M.2 hanging off the PC, so the Mac cannot write to it and the paths inside a
project mean nothing over there. Syncthing was mirroring the whole music folder and it is
agony: hundreds of thousands of tiny files, hashed and indexed continuously on both sides,
for a tree that changes twice a month when a pack gets bought.

And the projects it carried across could not be opened anyway. FL hunts for every missing
sample by walking every search folder, which takes minutes on a library this size.

What already works is a zipped loop package - the project plus only the sounds it actually
uses. That is the whole insight: a beat references 30 samples out of 326,000, so moving
the project is a thousand times cheaper than moving the library.

## What was measured

From `example.zip`, an ordinary beat exported as a zipped loop package by FL Studio
26.1.2.5557. The FLP is 344,192 bytes, 5,455 events, and the package holds 29 wavs flat
beside it - no folders.

**Event 196 is the sample path.** UTF-16LE, null-terminated. 30 of them for 29 unique
files, one sample being referenced twice. That is an exact match for the package contents:
event 196 alone is a complete inventory of what a project needs.

**The paths are absolute, and they are dead.** Every one of them reads

    C:\Users\deadm\AppData\Local\Temp\Image-Line\15776-{D9812A68-...}\{1F6BE85D-...}\MAPLE BASS.wav

which is FL's own temp staging folder from the moment it built the package. GUID-named,
per-export, and long since gone from the PC that wrote it. The package still opens on both
machines.

**So FL resolves by proximity.** It looks in the FLP's own folder, by basename, and the
stored path is decoration. Nothing else explains a dead Windows temp path loading instantly
on a Mac. FL does not write relative paths even in its own packages - it does not need to.

**The walk came back clean** on this file: 5,455 events terminating exactly on the declared
end of `FLdt`. The desync documented at `src/main/flp.ts:218` for FL 25.2.4 did not bite
here. One file is not a corpus, but it is encouraging.

**Other events worth knowing:** 199 is the version string and the one ASCII text event.
201 is the generator type and 203 the instance name, so `201 == "Fruity Wrapper"` followed
by 203 gives the plugin list - this project runs six instances of Serum 2. 193 carries
channel display names. 213 is the plugin state blob, and `Y:\VstPlugins(x64)\soothe2_x64.dll`
sits inside one of them.

**Compression is worth having but is not uniform.** The package deflates to 48% of its
size, and the spread is wide: 7-8% off dense full-length audio, 53-60% off sparse one-shots.
(An earlier guess in conversation put WAV at ~15% and was wrong in both directions.)

## The shape of it

Two umakbang instances, paired. The PC serves; the Mac takes.

**A remote machine is a root, not a mode.** The app stays exactly as it is locally, and a
remote folder can simply become the active root. This is the decision everything else hangs
off, and it works because the renderer only ever sees `Track` objects and
`window.umakbang.fileUrl(path)` - neither of which cares where the bytes are. Browsing,
search, sorting, waveforms and audition all come across for free.

**Devices is its own sidebar section, under Folders.** Folders stays purely local, so the
section a root sits in is what tells you which machine you are looking at. A device expands
to its roots with their counts; clicking one makes it active exactly as clicking a local
root does. Devices carries its own `+` for pairing, matching the affordance Folders already
has. The breadcrumb leads with the device name - `typhoon-pc > Library > SECRET SAUCE` - so
the one thing that changes when you are remote is the thing that says you are remote.

**A device serves its metadata with its index.** Tags, ratings, notes and detected tempo and
key are keyed by absolute path, so a Mac pointed at the PC's library has nothing to show for
`E:\...` and the whole left rail - Rated, the tag cloud, the counts - would read as empty.
They have to come from the machine that owns the files, which makes browsing the PC from the
couch look exactly like sitting at the PC. The alternative is a second, parallel, empty set
of tags per machine, which is worse than having none. These maps already travel together in
`bundle.ts` for settings export.

**Remote is read-only.** No rename, move, copy, delete, new folder or drag-to-move over the
wire, and no tag or rating edits either - the server answers GET and nothing else. Not
because RPC-ing `fs-ops.ts` is hard, but because of what trails behind it: undo is built on
local filesystem operations, drag-to-move between a local and a remote root is a transfer
rather than a move, and Quick move would quietly mean two different things depending on
which root you were in. Grey the mutating menu items with a reason rather than
half-supporting them.

The cost is that starring or tagging something while browsing the PC from the couch does
nothing, which is a fair share of what browsing is for. Worth revisiting once the rest
works - it is two endpoints and a write-back, not a redesign - but a server that cannot be
made to write anything is the better thing to ship first.

**Offline is nearly free.** With the device asleep the root still appears, backed by its
cached index, and the rows dim in place - the idiom 0.1.2 already introduced for files that
went missing. The whole library stays browsable and searchable from anywhere; only audition
and packing need the device awake.

**Packing never writes to the FLP.** Read event 196, copy those files flat beside a copy of
the project, and FL finds them by proximity. No re-encoding, no varint re-emission, no way
to corrupt a project. The packer is a copy tool wrapped around a reader.

**Packing and transferring are the same pass.** `GET /pack?flp=...` parses the project and
streams a tar built on the fly, straight from library files into the socket. No staging
directory, no temp copy, no zip step. FL does three passes over the data to make a package;
this does one, and the transfer starts immediately rather than after a wait.

**The package is the project once it comes back.** No relinking into the library, no
writing back to the original location, no merge. Authority is decided by hand, and the app
annotates rather than enforces: the original row gets a *superseded by `<package>`* label so
the stale copy is never opened blind. There is no three-way merge for a binary DAW project
and there never will be, so the only honest model is one holder at a time - made visible,
not locked.

**A returned FLP cannot simply overwrite the original**, and this is the reason the shape
above is the only one available without a writer. The packaged project opens by proximity;
put that same FLP back at `SECRET SAUCE/adore.flp` and its 29 samples are nowhere near it,
proximity fails, and FL falls back to the recursive hunt - the original problem, recreated
inside the library. So the choice is what shape a project takes from now on, not replace
versus keep:

*Shape 1, shipped in v0.2* - the package lands as `SECRET SAUCE/adore/`, holding the FLP
and its samples. Self-contained, opens anywhere, needs no writer, costs about 16MB of
duplicated samples per project.

*Shape 2, later* - rewrite the returned FLP's event 196 paths back to real library locations
and put it back as a bare `adore.flp` like every other project. No duplication, tidy
library, but it brings back the writer and with it the roundtrip gate and the corpus run.
One thing makes it cheaper than it first looked: **the packer already knows the mapping.**
Ship the pack manifest with the package and the return is an exact inverse - no hashing, no
index lookup - with only genuinely new files needing placement.

**The arrival prompt names the choice rather than the verb.** The old FLP is never deleted,
only labelled, which makes "replace and keep" stop being a separate option and makes
"replace, destroying the only other copy" not worth offering:

    adore came back from typhoon-mbp
    Worked on for 2h 14m. 29 samples unchanged, 2 new: vocal take 1.wav, riser.wav.

      Use the returned version   (original marked superseded, kept)
      Keep both, decide later
      Discard the return

The time is free: event 237 carries cumulative time-open and `parseFlpProjectTime` already
reads it, so diffing it against what was sent says how much work came back.

## Decisions, and why

**Plain HTTP/1.1 from `node:http`.** Range requests come free, which is exactly what
`src/main/protocol.ts` already needs, and the whole thing is debuggable with curl.

**Endpoints, all GET, with deliberately different shapes.** As built:

    GET /hello                              identity, libraries, generation per library
    GET /index?library=<id>                 the index NDJSON, gzipped
    GET /index/patch?library=<id>           the journal since, gzipped
    GET /file?library=<id>&rel=<rel>        bytes, Range-aware, never encoded

`/index` is gzipped because it is text and compresses 5-10x - at 241MB it is by a distance
the largest transfer in the system. `/file` deliberately is not: audio barely compresses, and
an encoded body cannot be range-requested, which would cost seeking. `/pack` will stream a
tar at a low deflate level - measured at roughly half on a real package.

`rel` is passed exactly as the index writes it, which means it is prefixed by the root's
*label* rather than its folder name (`scanner.ts:437`), and the label is something the user
can rename. The server strips that prefix by agreement and the containment check is what
actually decides.

**Read-only is enforced at the method, not per route.** Anything but GET or HEAD is a 405
before the route table is consulted, so a route cannot accidentally become writable.

**Every refusal is a bare 404.** Outside the library, missing, a symlink pointing out of the
tree, a NUL byte - all the same answer. Distinguishing them would let anyone on the tailnet
map the disk one request at a time.

Verified against the real library: traversal (`../`, absolute, percent-encoded, NUL-byte),
symlink escape by file and by directory, unknown library id, and a missing parameter all
return 404, while real files return 200 and honour `bytes=0-99`, `bytes=-50` and a 416 for an
unsatisfiable range.

**Index sync reuses the patch mechanism.** The index is already JSONL on disk
(`indexFileFor`), `bundle.ts` already streams gzip, and `appendIndexPatch` / `readPatches`
already do incremental updates. Ship the index once, serve patches after. The remote sync
protocol turned out to be one that already exists for local use.

**Tailscale is the security model.** Not a fallback for working off-network - the only
transport. The server binds to the tailnet interface and nothing else, so the tailnet is the
authentication boundary and WireGuard is the encryption. That deletes pairing codes, token
management and the TLS question in one go, and it makes home and the road the same code
path.

It also deletes discovery. MagicDNS resolves `typhoon-pc` from anywhere, and
`tailscale status --json` enumerates the tailnet with online state - so the Devices section
can populate itself from the peers already there and probe each for the umakbang port.
There is no pairing flow to build.

**Identification is a knock, not a file.** `GET /hello` on a fixed port with a short
timeout, every online peer in parallel: answers in umakbang's dialect and it is a device,
times out and it is not. One response carries discovery, identity and cache continuity
together -

    { "app": "umakbang", "protocol": 1,
      "device":    { "id": ..., "name": "typhoon-pc", "os": "win32", "version": "0.2.0" },
      "libraries": [ { "id": ..., "label": "Library", "path": "E:\\Music",
                       "files": 326555, "generation": 4711 } ] }

Storing an identity in the `.umak` bundle instead would be circular - the Mac cannot read
the PC's bundle without having already connected to the PC.

**The ids exist for continuity, not discovery.** Having pulled 326,555 rows once, the Mac
needs to know *this is the library I already cached* so it can ask for patches from
generation N rather than fetching everything again. The same id says when a library was
rebuilt or cleared, and tells two roots on one device apart.

They must never travel. Device id per install and library id per root, both in `userData`
with an entry in `LOCAL_ONLY` (`store.ts:532`), for exactly the reason written there for
`bundleExportDir` and `outputDevice`. Carried in a settings export, a restored backup would
make the MacBook claim to *be* the PC's library - one identity on two machines, and an index
cache quietly wrong ever after.

**List every peer, not just the serving ones.** "Why isn't my laptop showing up" is the
question this feature will generate most, and a greyed row reading *umakbang not running*
answers it on sight where an empty list just looks broken. Four states: serving, which
expands to its libraries with counts; online but not serving; offline, greyed with a last
seen, still expandable against a cached index because browsing offline is the point; and
relayed, marked, because DERP is fine for packages and bad for audition. With Tailscale
itself down the section says so rather than showing nothing.

Serving is a Settings toggle, defaulted on - the tailnet is already the trust boundary and
the library is read-only - but visible and switchable rather than implicit.

The cost is an outside dependency: no Tailscale, no feature. For two personal machines that
is a fair trade.

**Two things Tailscale does not cover.** *Binding* is now the single security-critical line
in the codebase: resolve the tailnet address explicitly, fail closed when the interface is
down, and never fall back to a LAN bind. Serving `0.0.0.0` would hand the entire library,
unauthenticated, to whatever coffee-shop WiFi the laptop is on. And *path containment* still
has to be ours - Tailscale authenticates the device, not the request, so canonicalise every
requested path and verify it sits under a configured root.

**Relay state cannot be read cold.** This was wrong in an earlier draft. Measured against
the real `tailscale status --json`: `CurAddr` is empty and `Active` is false for every peer
while nothing is talking to it, and `Relay` is only that peer's home DERP region - not
evidence that anything is being relayed. Direct-versus-relayed is knowable while a transfer
is running and not before, so the device row cannot carry it at rest.

**The server is a utility process.** `utilityProcess.fork`, the same as the scanner and for
the same reason: serving is sustained I/O, and doing it on the thread that runs the window is
how an app stops answering. It suits the split better than the scanner does, because nearly
everything it serves - the index, cached peaks, sample files, a packed project - is already
a file on disk, so the child reads its own way there and the parent holds only what is
genuinely the parent's: what the settings say and where Tailscale is. A fault parsing
something that arrived over a socket then costs a respawn rather than the app. Verified by
killing the child: browser process and renderer both survived, the port was released.

**A crashed server does not come back on its own** yet. The parent reports it and waits to
be asked again, which matches how the scanner behaves, but the Devices section needs either
a way to trigger the restart or a single retry with a backoff.

## Deliberately not built

Packages run 8MB to maybe 100MB, a few hundred at the worst. That is a second over gigabit
and under ten on WiFi, and it takes a whole category of engineering off the table.

- **No resumable transfers.** No chunking, no partial-file state. A failed transfer retries
  from the start, because starting again costs seconds.
- **No background job system.** Parse, read, stream - the whole operation is seconds. Double
  -click, a short progress bar, FL opens. No queue and no "your package is ready".
- **No eviction pressure.** Ten projects at 50MB is 500MB. The list of what has been taken
  is for knowing, not for reclaiming, and returned packages can simply stay as a free local
  copy of everything worked on away from the desk.
- **No content-addressed sample cache.** Five projects sharing an 808 will fetch it five
  times. At these sizes that is a rounding error and deduplicating it would be a fiddly
  subsystem earning nothing. Written down so it does not get built later out of tidiness.
- **No library mirror.** The thing this replaces.

## The hazard

A plugin missing on the Mac is stubbed out by FL, and saving can drop its state. Open this
example on a machine without Serum, save, send it back, and six channels have lost their
settings. That is real work destroyed, silently, and no amount of sample handling prevents
it.

The check is cheap: the plugin list is readable from events 201 and 203 at pack time, and
the Mac can enumerate its installed VSTs. Compare, and warn before anything transfers. This
is the one place the app should be loud rather than merely annotative.

The same limit applies to samples referenced from inside plugin state - Kontakt libraries,
DirectWave, a custom Serum wavetable. Those live in opaque blobs and cannot be packed.
Native channels and audio clips can.

## Open questions

**Basename collisions.** Flattening means two different `kick.wav` from different packs
collapse onto one file, which is silently wrong audio rather than a missing-file error. No
collision occurred in the example, so FL's own handling is still unobserved - and it does
not matter, because umakbang is doing the flattening and the rule is ours to pick. Cheapest
safe rule: hash on collision, and where contents differ, rename the second and write the
FLP for that one reference. Which brings the writer back, but as a rare path touching one
string rather than the default path touching all of them.

Worth running the collector across the whole library to find out how often this would
actually fire.

## Settled: the walk

The event stream desync is fixed, and it was never a version quirk. Two events break the
id-range rule that says ids 128-191 carry a dword: **169 carries eight bytes and 172 carries
five.** A walk that believes the rule loses the stream at the first one it meets, and every
id after that is read out of the middle of somebody else's payload.

Measured over all 2,796 projects in this library:

| rule | clean | desynced |
| --- | --- | --- |
| id-range only | 2,774 | 21 |
| plus 169 = 8 | 2,789 | 6 |
| plus 172 = 5 | 2,779 | 16 |
| both | **2,795** | **0** |

Neither widening breaks a file that already parsed. The one file left out is not an FLP - it
has no `FLhd` and never did.

With that in, collecting sample paths works across the library: **73,818 references across
2,764 projects, no desyncs.** `scanForTempo` stays as a fallback rather than a workaround,
since a third mis-sized event in a future format would otherwise take the tempo with it.

That was the gate. Everything below it can proceed.

## Built so far

A remote library is a root. `scanOne` returns `scanRemote` when one is, downloading the
peer's index instead of walking a disk; `protocol.ts` branches on `rootFor(...)?.remote` and
forwards the Range to the peer instead of opening a file. Nothing else changed - the
sidebar, search, sort, waveforms and the transport all work on a peer's library without
knowing one exists. `player.ts:267` is untouched.

That worked because `shared/roots.ts` already folded separators and matched root prefixes
case-insensitively, written for Windows disagreeing with itself. A `Z:\...` path resolves on
a Mac for free.

**Labels never go on the wire.** A label is the local name for a folder - the same library is
`SECRET SAUCE` on the machine serving it and `SECRET SAUCE (jkpc)` on the one that mounted
it - so the two ends can never agree on one. Paths are sent relative to the root with no
label, and the server does not strip one (which also made a real subfolder of that name
unreachable).

**Read-only is enforced twice.** Every file-mutating item is *absent* from the menu on a
remote selection, and every write in the store refuses a remote path - the keyboard never
goes near a menu. Both the selection and the destination are checked: acting on remote files
and pasting into a remote folder are different failures.

**Copying here is a copy, never a move**, since the source cannot be changed. It lands flat
under the file's own name in a folder set under Settings → Remote, and never overwrites.

### What the measurements changed

The peer is not on the LAN - 87ms away, direct, not relayed - and at that latency a single
stream is limited by what fits in flight rather than by the link:

| streams | throughput |
| --- | --- |
| 1 | 0.9 MB/s |
| 4 | 3.6 MB/s |
| 8 | 13.8 MB/s |
| 24 | 16.2 MB/s |

Files are fetched as 2MB ranges handed out from a queue across 8 pooled connections. Fixed
*equal* chunks were tried first and were wrong: the copy then ends at the speed of its
slowest chunk, which is quick to the nineties and then a long tail. Same 40MB, 6.0 MB/s split
eight ways against 14.5 MB/s from a queue.

A parallel fetch can also write a file of exactly the right size with the wrong bytes in it,
so `/hash` was added and the result is checked **before** the rename - a file that has taken
its real name is indistinguishable from one that arrived intact.

### Still single-stream

The index pull, at 9.95MB a launch. It cannot be ranged the same way because it is gzipped on
the fly and a compressed stream has no stable offsets. The fix there is the generation check,
which skips the transfer entirely on the launches where nothing changed - which is most.

Steps 1 through 3 are independently worth having. Nothing after step 1 should start before
the corpus agrees.
