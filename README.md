# umakbang

*it's pronounced oo-mahk-bahng*

A desktop file explorer built for a music production library - samples, stems, demos and
DAW project files in one indexed, auditionable list.

Electron + React + TypeScript, Tailwind CSS v4, shadcn-style components. Runs on Windows,
macOS and Linux from the same source.

## What it does

- **Browses like a file manager** - subfolders appear as rows and you drill into them,
  rather than every file being dumped in one list. Breadcrumbs, an up button and
  `Backspace` walk back out. Searching inside a folder covers its whole subtree.
- **Manages files like one too** - multi-select with ctrl and shift, then cut, copy,
  paste, duplicate, rename, delete, or make a new folder, from the context menu or the
  usual shortcuts. Deleting goes to the recycle bin. Folders can be moved and copied
  whole, and the library updates in place rather than rescanning.
- **Files things where they belong, quickly.** Drag a selection onto any folder row, onto
  a breadcrumb in the path bar to send it back up the tree, or onto the up button. For the
  folders you use constantly - a stems folder, somewhere for the rejects - name them under
  Settings → Quick move and they appear in the row menu under "Move to".
- **Indexes a folder tree** and streams results in as it walks, so a 30k-file library is
  browsable in a second rather than after a full scan.
- **Reads real audio metadata** - duration, sample rate, bit depth, channels, bitrate,
  plus BPM and musical key - straight from container headers. No native modules.
- **Shows file type**, not a guess at purpose. Every row carries an icon - a waveform for
  audio, a note for MIDI, a fader page for a DAW project - in the same colour as the Type
  column, which spells out the extension. What a file is *for* is yours to record with
  tags: folder and file naming is far too inconsistent to infer reliably, and a wrong
  badge on every row is worse than no badge.
- **Plays anything in-window.** Every row draws its own waveform, and the playing row is
  the scrub target - click or drag along it to move through the track. The same waveform
  sits in the player controls, since the row it belongs to is often scrolled away or in a
  folder you've navigated out of. The queue fills automatically from the folder the file
  lives in (or from the current filtered list).
  Playback never moves the list: auto-advance and skipping change what you hear, not where
  you're standing. The player bar's "show playing track" button goes to it on request.
- **Detects tempo** by analysing the audio, for files whose headers and names don't say.
  It rides on the decode the waveform already performs, so browsing fills BPM in as you go.
- **Star ratings and tags**, stored locally. `1`–`5` rates whatever is selected and `0`
  clears it; `T` tags it, several files at a time. Every tag in the library sits as a chip
  above the transport, and clicking one narrows what you're already looking at rather than
  taking you somewhere else.
- **Carries its settings between machines** - Settings → Backup writes every preference,
  tag, rating and detected tempo to one file. Import it on the new machine and point it at
  your library; nothing else needs setting up again. **One is written on its own once a
  day**, into a `backups` folder beside the app unless you point it somewhere else, so the
  months of tagging behind a library survive whether or not anyone remembers to press
  Export.
- **Real-time visualizers** - spectrogram, spectrum, rolling waveform, scope, levels and a
  stereo/goniometer field - in a dockable panel, or filling the window on their own. They
  hold their last frame over a short pause and wipe themselves once silence has lasted five
  seconds, so a stopped player never looks like a live one.
- **Shrinks to a mini player** - a 300px square parked at the top of the display and kept
  above everything else, with the name, a scrubbable waveform and the transport. For when
  umakbang is what's playing while you work in the DAW. One button back to the library.
- **Production stats** read from FL Studio's per-project time tracking: hours actually
  spent, when you work, and where the time goes.

## Running it

```bash
npm install
npm run dev
```

`npm run typecheck` covers the main, preload and renderer projects separately.

## Building

```bash
npm run pack        # unpacked app in release/, no installer - fastest
npm run dist:win    # NSIS installer
npm run dist:mac    # dmg + zip (arm64 + x64)
npm run dist:linux  # AppImage
```

Each platform's installer must be built **on that platform** - a macOS `.dmg` cannot be
produced from Windows. The source is fully cross-platform; only packaging is host-bound.

Icons are generated by electron-builder from `build/icon.png` (1024×1024), with
`build/icon.ico` supplying crisp small sizes on Windows.

## Running it from one folder

Unzip `umakbang-0.1.0-win.zip` anywhere - a USB stick, a second machine, a folder you can
delete afterwards - and run `umakbang.exe`. That folder holds the whole app.

By default it still keeps settings, tags, ratings, detected keys and its index caches under
`%APPDATA%\umakbang` on whatever machine it's plugged into. To keep those in the folder too:

```
umakbang/
  umakbang.exe
  data/          <- make this folder; that's the whole switch
```

With `data` present, everything umakbang remembers lives inside it and nothing is written to
the host. Delete the folder and it goes back to normal. It has to be created by hand rather
than shipped, because the installer and the zip are the same bytes - a marker packed into
the build would make installed copies portable too.

Two things to know:

- **A portable copy never self-updates.** Updating on Windows means running an installer,
  which would install to the host machine instead of replacing your folder. Settings →
  Updates says `portable copy`. To update, unzip the new version over the old one, keeping
  your `data` folder.
- **Library folders are still absolute paths.** If your samples are on the same stick, its
  drive letter can differ between machines and the library will point at nothing. Settings →
  Import can remap them, which is what it exists for.

## Forking it

Two things are worth changing before you publish a build of your own.

**`electron-builder.yml` → `publish.owner`.** That block becomes the `app-update.yml` packed
beside the app, and it decides which repository your users are offered updates from. Leave it
and they get this one's builds installed over yours.

**Nothing else.** There is no token to arrange - releases are read without a credential, and
`GH_TOKEN` is only needed in the environment when *you* publish (`npm run release`), where it
wants write access to your own repository's contents.

## Search syntax

Bare words match the file name and its path. Prefixed terms narrow by field, and
everything is ANDed together.

| Term | Matches |
| --- | --- |
| `vox` | name or path contains "vox" |
| `kind:project` | audio, midi, project |
| `ext:wav` | file extension |
| `bpm:128` | tempo, tolerant of rounding |
| `bpm>120` / `bpm<90` | tempo range |
| `key:Am` | musical key |
| `dur>60` / `len<10` | duration in seconds |
| `tag:keeper` | your own tags |
| `stars:4` | exact star rating |
| `stars:3-5` | star rating range |
| `stars>3` | rated above 3 |

A text search sorts by relevance and always covers subfolders. Field-only filters keep
whatever column sort you had.

For the common case there's no need to type anything: the funnel menu in the toolbar lists
every kind and extension actually present in the library, with counts, and toggles them as
filters. It also holds "Sort by type" - the same thing clicking the Type column header
does. Tags filter the same way, from the strip above the transport.

Filters stack - a search, a type, a tag - and a view narrowed by one you've forgotten
looks exactly like a library that has lost your files, so the toolbar grows a **Clear**
button counting whatever is currently narrowing the list.

**Sort is remembered per folder.** Stems want to be in name order and a bounces folder
wants newest first; sorting one doesn't disturb the other, and folders you've never sorted
follow the library default (newest first).

Copy also puts the paths on the system clipboard, so a paste outside umakbang - a DAW's file
dialog, a terminal - gets something useful. Pasting *into* umakbang uses its own clipboard.

## How it's put together

```
src/main/       Electron main - scanning, metadata probing, persistence, file protocol
src/preload/    contextBridge API surface
src/renderer/   React UI
src/shared/     Types and file classification used by both sides
```

A few decisions worth knowing about:

**Metadata is parsed in-house** (`src/main/probe.ts`). WAV, AIFF, FLAC, MP3, MP4/M4A and
Ogg/Opus headers are read directly - a few hundred KB per file rather than a decode. This
avoids an ESM-only dependency in a CommonJS main process, keeps a full-library pass fast,
and gives exact bit depth for the uncompressed formats that matter most here. Tempo also
comes from the ACID chunk in loop libraries and from ID3 `TBPM`/`TKEY`, falling back to
conservative filename parsing.

**AIFF is rewrapped, not decoded** (`src/main/aiff.ts`). Chromium ships no AIFF decoder,
but AIFF and WAV are both raw PCM in different containers, so the protocol handler swaps
the container and byte order on the fly. Logic and Pro Tools stems play like anything
else.

**Files are served over a `umakbang-file://` scheme** (`src/main/protocol.ts`) rather than
`file://`, which keeps `webSecurity` on. Two things about it are load-bearing:

- The scheme needs `corsEnabled` *and* an `Access-Control-Allow-Origin` header. An
  `<audio>` element loads cross-origin without CORS, but the waveform builder has to
  `fetch()` the bytes to decode them.
- Files are read and streamed by the handler itself instead of being delegated to
  `net.fetch`, so responses carry a real `Content-Length` and honour byte ranges. Without
  those a media element can play a file but never learns its duration or seeks within it -
  the timeline sits at 0:00 and clicking the waveform does nothing.

**The waveform is pre-rendered** into two offscreen canvases (played and unplayed tints)
whenever the peaks or the size change, so a frame is two `drawImage` calls instead of a
thousand `fillRect`s - and the animation loop only runs while audio is actually moving.

**Persistence is plain JSON** in `userData` (`src/main/store.ts`), written atomically and
debounced. A native SQLite build would need rebuilding per Electron version and per
platform, which is a bad trade for a few thousand rows. The two big caches are the
exception: the metadata cache and the file index are append-only NDJSON, because
re-serialising a 300k-entry document on every update blocks the process for seconds.

**Scanning runs in a utility process** (`src/main/scanner-process.ts`). Walking a large
tree and probing metadata is sustained CPU and I/O; on the browser process it starves the
window's message pump badly enough that Windows closes the app as unresponsive. The file
index is saved after each scan and replayed on the next, so a quarter-million-file library
is browsable a few seconds after launch while the real walk re-validates behind it.

**File operations report what they did, per file** (`src/main/fs-ops.ts`). A moved folder
comes back as the list of files that went with it, each paired with where it used to be, so
the renderer can move its rows, carry ratings, tags and already-probed metadata across, and
append the change to the index journal - instead of rescanning a quarter-million files over
a drag and drop. Empty folders have no file to stand in for them in the folder tree, which
is derived from the index, so they're grafted on by hand until a scan finds them.

**Waveform peaks are computed lazily**, per row, as rows scroll into view - two decodes at
a time, cached to disk forever after. Pre-computing them for a whole library would be
hours of decoding for data most of which is never looked at.

**The track index is mutated in place** during scanning, with a `revision` counter as the
change signal, rather than copying a 30k-element array on every metadata batch.

**Row icons come from the OS** (`src/renderer/src/lib/file-icons.ts`), so a `.flp` carries
FL Studio's own logo. `app.getFileIcon` is a shell call, so it's made once per *extension*
rather than once per file, and only for extensions actually on screen. Folders keep a drawn
glyph: Windows' folder icon is built for 16px and up and turns to mush at the size these
rows use.

**There is no light mode.** umakbang is a dark app and the stylesheet's `.dark` class is
fixed on `<html>`, so nothing has to re-derive colours when a mode flips. The accent and
background are still yours to set in Settings; they're written as inline custom properties,
which beat the stylesheet either way.

**The app was called cove.** Electron files an app's data under its name, so the rename
would have handed every existing install an empty folder next to a full one - `store.ts`
adopts the old directory's contents the first time it finds none of its own, copying rather
than moving so an older build still opens.

## Notes

- umakbang never writes to your audio files. It does move, copy, rename and delete them, but
  only when you ask: nothing in browsing, scanning or playback touches the disk. Deletes
  go to the recycle bin, and a copy or move never overwrites - a name that's taken becomes
  "name (2)".
- Files can be dragged straight out of the list into a DAW or a browser - hold `Alt`
  while you drag. A plain drag stays inside umakbang, for filing things into folders.
- Waveform peaks are cached to disk after the first play, so a file is decoded once.
- `.wma`, `.mid` and a few others are indexed and revealable but not previewable; they're
  shown greyed out with a note in the player rather than failing silently.
